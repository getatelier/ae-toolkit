# PRD: Roadmap Phase 3 — Enforcement Walls

## Overview

Phase 3 of the AET roadmap (`content/fable-review/09-2026-07-10-roadmap.md`): completes what frh-11/13/14/17 started and makes the doc 06 P1 invariant demonstrable — _the CLI is the only legitimate writer; hooks make illegitimate writes fail; tamper-evidence makes the ones that slip through visible._

**Deployment scope — this phase delivers Mode 1.** The roadmap now distinguishes two deployment modes (doc 09, "Two deployment modes"). **Mode 1 — non-invasive single-operator use**: AET run by one person on a repo whose team does not use it — plans/PRDs versioned like any project doc, GitHub issues optional, and _no AET config required in the shared repo and no AET ref pushed to the shared remote_. **Mode 2 — team-shared state with server-side forge enforcement on GitHub/Azure DevOps**: a named, separate roadmap phase (doc 09 Phase 6), deferred here by design. Phase 3's walls are the single-operator floor and the substrate Mode 2 builds on; they are correct for Mode 1 and never contradicted by Mode 2.

Five pieces: `aet gate submit` centralizes and fail-closes verdict writing (fixing a live concurrency bug in the same pass); `aet hooks install` writes a **self-contained** pre-push hook so a task branch cannot be pushed without recorded gate evidence — installable in a repo that commits nothing else about AET; git-refs becomes the default task-storage backend, keeping the ledger in `.git` (`refs/aet/*`, unpushed — invisible to the shared tree); GitRefsBackend gains its own tamper-evidence mechanism so the "hand-edited ledger" exit-gate claim is true for the backend that is actually the default once this phase lands; and a **relocatable external config root** lets AET's backend/mode config live under `~/.aet/{slug}/` so a Mode-1 project's tracked tree carries no AET config — the task queue/history already move into `.git` via git-refs, and plans and PRDs remain versioned project docs in `docs/`.

## Goals

- **G1**: Gate submission is centralized and fail-closed — `aet gate submit` is the only writer of stage verdicts, schema-validates per gate type, and fails closed on missing or malformed input rather than silently succeeding; the concurrent group-session path bug that caused false stage failures (thp-04) is fixed at the root (R-1, R-2, R-3).
- **G2**: The CLI is the only legitimate writer, enforced at the git boundary — `aet hooks install` installs a self-contained pre-push hook so a task branch cannot be pushed without recorded gate evidence, regardless of which harness or agent attempted the skip, and it installs on a repo that commits nothing about AET (R-4).
- **G3**: The ledger is git, and tampering with it doesn't go unnoticed — git-refs becomes the default task-storage backend, and a hand-edited ledger write is mechanically detected, not just theoretically detectable (R-5, R-6).
- **G4**: The exit gate is demonstrated, not asserted — an adversarial rehearsal proves both enforcement walls under real attempted violations, including in a non-invasive config-external checkout, and the result is recorded (R-7, R-8).
- **G5**: AET runs non-invasively — on a repo the rest of the team does not use for it, a full plan→ship lifecycle keeps AET's backend/mode config out of the tracked tree and pushes zero AET refs to the shared remote; the config resolves from a per-project external root, plans and PRDs remain versioned in `docs/` (project artifacts, not tooling), and `aet hooks install` needs nothing committed to work (R-4, R-9, R-10).

## Non-Goals

- No `aet desk`, `aet plan validate`, or zero-review-class mechanism (Phase 4).
- No failure taxonomy, circuit breaker, stall watchdog, or budget ceilings (Phase 5).
- No multi-harness adapters, `aet doctor`, or cross-vendor review routing (Phase 6).
- No scoreboard, `aet eval`, or learning loop (Phase 7).
- No shared fail-closed helper for hypothetical future interactive CLI prompts. Verified against the codebase: there is currently no `input()`/stdin call site anywhere in the toolkit — HARD GATEs (`aet-plan`, `aet-pipeline-plan`) are prose-only, live-chat conventions, not code the orchestrator executes unattended. R-2 covers only `aet gate submit`'s own argument/evidence validation; a general-purpose primitive is deferred to whenever a real interactive consumer exists (see Open Questions).
- No change to git-refs's local-only-by-default push policy (frh-13) — pushing `refs/aet/*` remains a manual, documented choice. Sharing the ledger across a team (a portable sync branch, so state travels without depending on forge-specific custom-ref support) is Mode 2, the named team phase (roadmap doc 09 Phase 6), not this phase.
- **No Mode 2 team infrastructure.** Server-side forge enforcement — GitHub branch protection + required checks, Azure DevOps branch policies + build validation — and shared-ledger transport are the named team phase (roadmap doc 09 Phase 6). The pre-push hook here is the single-operator floor, not team-grade enforcement: a teammate on a fresh clone without the hook, or a `--no-verify` push, is a Mode 2 concern closed server-side. Phase 3 does not claim to stop them and its rehearsal (R-7) will not assert it does.
- **No forge-native storage backend.** GitHub-issue projection (existing `GitHubBackend`) — and any later Azure DevOps work-item projection — stays optional and one-way; git-refs remains the single source of truth (standing fence, roadmap doc 09: no second storage backend beyond git-refs). Creating issues is a Mode-1 convenience the operator toggles, never a requirement.
- No retirement of the JSON backend code path — it remains available as an explicit config opt-out (`task_backend: "json"`), not deleted. "Demoted to disposable projection/cache" describes its role as default, not its removal.
- No cryptographic signing (GPG-signed commits/refs) for tamper-evidence — content-hash-based detection only, consistent with frh-17's existing approach; identity/signature verification is out of scope.
- No changes to the four evidence schemas themselves (frh-10's `qa`/`review`/`cso`/`sync-docs` `SCHEMAS`) — `aet gate submit` wraps existing validation, it doesn't redefine it.
- Standing fences hold (roadmap doc 09): no DAG/parallel stage graphs, no daemon, no plugin verifier APIs.

## Requirements

- **R-1**: A new `aet gate submit --stage <s> --verdict pass|fail --evidence <path>` subcommand — one additional row in the `aet` dispatcher's spec table (cli-01), exactly as that plan's own design anticipated ("Phase 3+ subcommands are one-row additions"). It wraps `aet-work/lib/evidence.py`'s existing `write_verdict`/`validate_verdict` (frh-10), schema-validating per gate type (`qa`, `review`, `cso`, `sync-docs`). The orchestrator's evidence gate (frh-11) becomes the only consumer of verdicts written through this path — no other writer is sanctioned.
- **R-2**: `aet gate submit` fails closed on malformed input: missing or empty `--verdict`/`--evidence`, an evidence file that doesn't exist or isn't readable, or a payload that fails `validate_verdict`'s schema check — each is a non-zero exit with a clear, named error, never a silent or implicit success.
- **R-3**: Fix the `AET_EVIDENCE_PATH` environment variable derivation in `run_stage_group` (`src/aet/cli/orchestrator.py`). Confirmed by inspection: `run_stage` sets the evidence path (`src/aet/cli/orchestrator.py`); `run_stage_group` does not. Under batch/group-session concurrency this forces a fallback to a CWD-derived project-slug path that can diverge from the path the gate actually reads — the confirmed root cause of thp-04 being marked failed three times despite complete, verified work. Every evidence-bound stage in a group session must publish a path the gate agrees on, unambiguously, including when a group runs more than one evidence-bound stage concurrently (a single stage cannot be assumed). **Satisfied by an existing plan, not a new one in this PRD's set**: `docs/plans/frh-18-group-evidence-path-contract.md` (`status: approved`, queued `ready`, `blocked_by: []`) targets this exact root cause with a canonical `resolve_verdict_path()` and per-kind `AET_EVIDENCE_PATH_<KIND>` precedence — a materially more correct design than this PRD's first draft (`ewl-02`, now abandoned; see Technical Notes). Because R-3 is satisfied outside this PRD's plan set, `ewl-01` (R-1) is `blocked_by: frh-18-group-evidence-path-contract` — `aet gate submit`'s `write_verdict` delegation should resolve destination paths through frh-18's corrected resolver, not the pre-fix ambiguous default.
- **R-4**: A new `aet hooks install` subcommand writes a **self-contained** `.git/hooks/pre-push` (generated hook body — no dependency on a committed `scripts/hooks/pre-push`), so it installs and works in a repo that commits nothing else about AET (Mode 1, R-9/R-10). For a push on a task branch, the hook refuses unless the branch's task has recorded gate evidence for its required stages (core qa/review, plus security/docs stages per the plan frontmatter's `security_review`/`docs_sync` routing keys). It enforces AET gate evidence **only**; any repo-specific build/coverage gate is delegated to an optional repo-local hook script the generated hook chains to _when present_ (preserving aiskills' own `make validate` gate) and simply absent in a client repo — never imposed on the team's pushes. Non-task-branch and pure-deletion pushes pass through untouched. This replaces waf-05's tracked-script-plus-manual-symlink install model (clean cut, no dual mechanism, per the project's no-backward-compat rule); `docs/CONVENTIONS.md`'s manual symlink instructions are replaced with `aet hooks install`.
- **R-5**: `GitRefsBackend` (frh-13/14) becomes the default backend in `src/aet/backends/factory.py` (for config key `task_backend`); the JSON queue file becomes a disposable, regenerable projection rather than the source of truth. Existing installs can opt back to `task_backend: "json"` explicitly. frh-14's parity suite (`tests/test_git_refs_parity.py`) is the safety net proving the flip is behavior-preserving and must stay green against the new default. Because git-refs keeps queue and history in `.git` (`refs/aet/*`, local-only/unpushed per frh-13), this default is also the **storage half of non-invasiveness** (R-9): task state never lands in a Mode-1 project's tracked tree or its shared history.
- **R-6**: `GitRefsBackend` gains a tamper-evidence mechanism with a guarantee equivalent to frh-17's JSON-wrapper `revision`/`content_hash` stamping (`src/aet/queue.py`), which has no git-refs counterpart today (`GitRefsBackend.seal` drops a ref and appends to history with no integrity stamp). A hand-edited or out-of-band-modified task ref or envelope blob (`refs/aet/tasks/<id>`, `refs/aet/meta/queue`) must be detected on next read and surfaced as a fail-closed integrity error, mirroring `QueueIntegrityError`'s contract — mutating paths fail closed; read-only paths warn and continue.
- **R-7**: The phase's exit gate is demonstrated end-to-end, not just asserted, and the demonstration is recorded (audit doc, matching frh-14's A/B-findings precedent):
  - (a) an agent instructed to skip gates and force-push a task branch is stopped by the installed pre-push hook (R-4) — scoped honestly to a single operator who has the hook installed and does not bypass it, since a fresh clone or `--no-verify` is a Mode 2 / server-side concern (Non-Goals);
  - (b) a hand-edited git-refs ledger write is surfaced by tamper-evidence on next read (R-6);
  - (c) the same two walls demonstrated in a **config-external** checkout — AET's config resolved from `~/.aet/{slug}/`, no AET config in the tracked tree, zero `refs/aet/*` pushed (plans/PRDs under `docs/` are expected versioned artifacts) — proving Mode 1's non-invasiveness is shown, not assumed (R-9, R-10). Where a Mode-1 project has no remote at all, (a) is N/A and the orchestrator's evidence gate (frh-11) is the operative wall — recorded as such.
- **R-8**: Tests: `aet gate submit` schema validation and fail-closed CLI behavior (R-1, R-2); `AET_EVIDENCE_PATH` correctness under concurrent group-session batch execution, regression-testing the thp-04 scenario (R-3); self-contained hook install with no committed `scripts/hooks/pre-push` present, plus the adversarial-push rehearsal (R-4, R-7a); git-refs default-flip parity still green (R-5); git-refs tamper-evidence detection of a hand-edited ref/blob (R-6, R-7b); a config-external lifecycle leaving the tracked tree free of AET config and the remote free of `refs/aet/*` (R-9, R-10, R-7c).
- **R-9**: A **relocatable external config root**. The AET backend/mode config is resolvable from a per-project external root `~/.aet/{slug}/config.json` — the same identity used for gate-evidence reports (ADR-019, `~/.aet/reports/{slug}/`), telemetry (ADR-012), and the locally-derived project slug (ADR-022). This closes the last un-gitignored AET artifact under `.agents/`: the queue/history (`.agents/work-queue.json`, `.agents/work-history.jsonl`) are already gitignored and move into `.git` via git-refs (R-5), leaving `.agents/aet-work.json` as the only AET file that would otherwise surface in a client repo's `git status`. **Plans and PRDs stay versioned in `docs/`** — they are project artifacts, not tooling, and are not relocated (owner decision, 2026-07-12).
- **R-10**: **External-first config resolution.** Config resolution checks env (`AET_PROJECT_ID` scopes the slug) and the external root `~/.aet/{slug}/config.json` _before_ any in-tree `.agents/aet-work.json`, falling back to built-in defaults — so keeping AET config out of a repo never itself requires an in-tree file. This closes the chicken-and-egg where the file that says "keep AET out of the repo" would otherwise have to live in the repo. No `sidecar|in-repo` mode enum is needed: `aet-setup` chooses where to _write_ config (external for a non-invasive project, in-tree for self-hosting), and reads are always external-first.

## User Stories

- As an agent completing a checking stage, I submit my verdict through one command, and if I get the invocation wrong the failure is immediate and legible instead of a silent pass that surfaces as a mystery failure three stages later (satisfies: R-1, R-2).
- As the owner running a night-shift batch, a group-session task's evidence lands where the gate actually looks for it, so a fully-completed task is never marked failed by a path mismatch again (satisfies: R-3).
- As the owner, I install one hook once (`aet hooks install`) and from then on, no task branch — mine or an agent's — reaches the remote without its gates having actually passed (satisfies: R-4, R-7a).
- As the owner, if someone or something hand-edits the task ledger outside the CLI, I find out the next time anything reads it, whether the backend is JSON or git-refs (satisfies: R-6, R-7b).
- As the Phase 4 implementer, I build `aet desk` and `aet plan validate` on a queue whose default storage is git-refs and whose gate evidence is verdict-driven, not footer-driven (enabled by R-1, R-5).

## Acceptance Criteria

- [ ] `aet gate submit --stage qa --verdict pass --evidence <path>` writes a schema-valid verdict that the orchestrator's evidence gate accepts; omitting `--verdict`, omitting `--evidence`, pointing `--evidence` at a missing file, or pointing it at a schema-invalid JSON payload each exit non-zero with a named error (satisfies: R-1, R-2).
- [ ] A 4-way batch run covering a `[reviewed, secure]` stage group writes both verdicts to the path `aet gate submit`/the gate reader agree on, under concurrent sibling tasks, with no path-derivation divergence (satisfies: R-3).
- [ ] After `aet hooks install`, pushing a task branch with an unrecorded required gate is refused by the pre-push hook; pushing a branch-deletion ref still short-circuits per waf-05; pushing a non-task branch runs the existing coverage gate unchanged (satisfies: R-4).
- [ ] With no `task_backend` configured, a fresh `aet-setup` run yields `git-refs` as the active backend; `tests/test_git_refs_parity.py` passes against it (satisfies: R-5).
- [ ] Hand-editing a task's git-refs blob content (bypassing the CLI) and then reading it through any `aet state`/`aet status` path raises a fail-closed integrity error instead of returning the tampered value (satisfies: R-6).
- [ ] `aet hooks install` run in a repo with **no** committed `scripts/hooks/pre-push` installs a working gate-evidence pre-push hook; where a repo-local hook script exists, the generated hook chains to it (satisfies: R-4).
- [ ] With AET config written to `~/.aet/{slug}/config.json`, a full plan→ship lifecycle leaves `git status` free of AET config and the shared remote free of `refs/aet/*` (plans/PRDs under `docs/` are expected versioned artifacts); the same run with in-tree `.agents/aet-work.json` resolves unchanged (satisfies: R-9, R-10).
- [ ] The adversarial rehearsal from R-7 is executed and its outcome — (a), (b), and the config-external arm (c) — is written up in `docs/audits/` (satisfies: R-7, R-8).
